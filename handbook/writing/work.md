# Work 작성법

대상: `src/content/pages/work.md`. About의 직장 경력과 달리 실제 수행과 기여를 기록한다.
원문 근거: SPHINCS+ Java 모듈 항목은 알고리즘, 언어, 호환 대상을 구체적으로 적는다. Standards는 Editing Assistant 등 참여 수준을 명시한다.

## 항목 템플릿

```markdown
- [프로젝트명], [공개 가능한 기관], [YYYY. MM. ~ YYYY. MM.]
  - [본인이 실제로 구현/연구/참여한 내용]
  - [관련 기술이나 제약, 필요할 때만]
  - [자료](실제 자료 주소)
```

기술 목록을 능력 배지로 바꾸지 않는다. 보조 참여를 주도/총괄로 바꾸지 않는다. 성과 수치와 고객명은 공개 가능 여부까지 확인한다. 프로젝트는 근무처별로 최근 순서로 묶고 Standards는 별도로 둔다. 고객/발주기관을 근무처로 혼동하지 않는다. 신규 설명은 간결한 영어로 쓰고 기존 한영 혼용 원문은 보존한다. AutoCrypt 항목은 직접 개발과 연구소장 책임 범위를 소개문으로 구분하며 모든 항목에 Led/Oversaw를 반복하지 않는다. 담당 기간을 확인하지 못한 신규 항목은 날짜를 추정하지 않는다. 조교/심사보조 같은 학술 활동을 재분류할 수는 있지만 사실관계와 역할은 보존한다.

## 묶음과 확인 사항

WAIS 5/6/8회, 조교 과목, 심사보조 학회처럼 반복되는 기록은 기본 HTML details/summary로 묶는다. 요약에는 내용을 알아볼 수 있는 제목을 쓰고 각 항목의 날짜와 자료 링크는 모두 보존한다. Markdown 목록 앞뒤에 빈 줄을 넣는다. JavaScript 없이 터치와 키보드로 열려야 한다.

소속이 명확한 프로젝트는 해당 근무처 아래 둔다. Other Research Projects는 소속을 특정하지 않은 연구 과제에 사용한다. 담당 기간을 확인하지 못한 항목에는 날짜를 추정해서 붙이지 않는다. 연구소 문서에 등장한다는 이유만으로 개인의 담당 업무로 간주하지 않는다. 역할과 수행 범위는 작성자 확인을 우선한다. 행사명과 날짜가 충돌하면 확인 후 정리하며 외부 검증 없이 정확한 개최일이라고 단정하지 않는다.

검수: 구조를 변경할 때 기존 항목과 첨부 링크의 전후 목록을 대조한다. 한 항목에서 어떤 일을 했는지 드러나는가? 팀 전체 성과를 개인 성과로 쓰지 않았는가? 기밀 정보가 없는가? 기간이 확인됐는가?
